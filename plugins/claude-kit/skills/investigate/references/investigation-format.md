# Investigation record format

**This file is the single owner of the on-disk investigation format.** The `investigate` and
`implement` skills both defer to it. Do not restate these rules in a SKILL.md body — restated
rules drift.

## Layout

```
.claude-sandbox/investigations/<slug>/
  INDEX.md            <- reconciled current view, rewritten wholesale every pass
  00_initial.md       <- append-only serials, never edited after they are written
  01_<what-it-adds>.md
  02_implementation.md
```

One directory per investigation series. A series is one problem followed from first
investigation through implementation, however many passes that takes.

### Slug

Kebab-case, derived from the problem, 2–5 words: `fix-sidecar-gitignore`,
`investigate-implement-skills`, `flaky-upload-retry`. Not the file it touches, not a date —
what the work *is*.

Before creating a series, list `.claude-sandbox/investigations/` and check for an existing
slug covering the same problem. Extending a series beats starting a near-duplicate. On a
genuine collision with unrelated work, disambiguate with a distinguishing word, not a number.

### Serial and name

`NN_<name>.md`, zero-padded from `00`. The name is a short kebab slug for **what this pass
adds**, not a restatement of the series slug:

- `00_initial.md` — always the first pass
- `01_cognito-migration.md` — a re-investigation that added the migration analysis
- `02_implementation.md` — the outcome file written by `implement`

**The highest serial is the newest. Never sort by modification time** — a file can be
rewritten in place by an editor or touched by a checkout without being newer in the record.

## The two rules

### 1. `NN_*.md` files are append-only

Once written, a serial is never edited and never deleted. A later pass writes a **new** file
at the next free serial. This makes the series an auditable log of how understanding changed.

Every file after `00` opens with a `Supersedes` block, immediately after the heading:

```markdown
## Supersedes

- `00_initial.md` § Proposed Fix — the retry wrapper is in `internal/http/`, not
  `pkg/client/`; the cited `client.go:88` no longer exists.
- `00_initial.md` § Open Questions — "does the queue have a DLQ?" is closed: it does
  (`infrastructure/queues.tf:42`).
```

Or, when nothing is invalidated:

```markdown
## Supersedes

Nothing — purely additive.
```

**Never omit this block on `01`+.** A reader composing the series has no other way to know
that an earlier statement is dead. Name the file, the section, and what specifically is now
wrong — not "some details changed".

**Declaring a closure in `Supersedes` is what actually closes it.** Omitting a resolved
question from the new file's own Open Questions is not enough: a reader cannot distinguish
"this pass closed it" from "this pass didn't mention it".

### 2. `INDEX.md` is rewritten wholesale

The index is a **current reconciled view**, not a log. Every pass regenerates it from the
composition of all serials. It is small, so rewriting it is cheap and always correct.

## Reading a series

**Read every `NN_*.md` in serial order, lowest to highest, applying each `Supersedes` block as
you go.** The composition of all files, in order, is the plan.

`INDEX.md` is a summary and is **never a substitute for the files**. Read it first for
orientation — provenance, what exists, what is still open — then read the files.

A consumer that reads only the index, or only the highest serial, will act on superseded
information. `implement` must read the whole series before writing code, and again before
resuming after any pause.

## Standard outline — `NN_*.md`

Open with the attribution line:

```markdown
> **Automated AI Investigation** — Generated by Claude Code (`investigate` skill) on
> {YYYY-MM-DD}. This analysis is a starting point and should be verified by a developer.

# NN — <title>
```

Then, in order. Drop a section only when it would be empty; the ones marked **never omit**
are written even when the answer is "none":

| Section | Notes |
|---|---|
| `Supersedes` | `01`+ only. **Never omit** there. |
| `Summary` | What the work is, in 2–4 sentences. |
| `Confirmed Assumptions` | Settled at the requirements gate. **Never omit.** |
| `Out of Scope` | What was deliberately excluded, and why. |
| `Existing Architecture` | Titled **`Root Cause Analysis`** for bugs. What the code does today. |
| `Implementation Approach` | Titled **`Proposed Fix`** for bugs. **Required** — `implement` refuses a series without it. Genuinely-open alternatives go here as sub-options. |
| `Files to Modify` | Per repo, with paths. |
| `Patterns to Follow` | Conventions the implementer must match. |
| `Blast Radius` | Consumers, public API, contracts, anything downstream. State "self-contained" explicitly when it is. |
| `Test Coverage` | What exists, what the change needs. |
| `Security` | Only when the change touches auth, secrets, input handling, or a trust boundary. |
| `Performance` | Only when the change is on a hot path or changes I/O volume. |
| `Infrastructure` | Only when new resources, config, or deploy artifacts are involved. |
| `Deployment & Rollout Notes` | Ordering, migrations, flags. |
| `Risk Assessment` | **Never omit.** |
| `Open Questions` | **Never omit** — "None" when there are none. |

### The outcome file (`implement` writes this)

Same outline, named `NN_implementation.md`, with `Implementation Approach` replaced by:

| Section | Notes |
|---|---|
| `What Was Built` | The actual change, per repo. |
| `Deviations` | Where the build diverged from the plan, and why. Files that turned out to be no-ops belong here. |
| `Verification` | The tier reached (see below) and the concrete evidence — command run, output, what was *not* covered. |
| `Follow-ups` | Documentation updates applied, work spun out, anything left. |

Its `Supersedes` block names each plan statement the build overturned, or
`Nothing — the plan held`.

## Standard outline — `INDEX.md`

```markdown
# <slug>

> **Automated AI Investigation** — Claude Code (`investigate`), last updated {YYYY-MM-DD}.
> Verify before acting.
>
> **Provenance:** `<repo>` @ `<short-sha>` · `<repo>` @ `<short-sha>`

<one-paragraph statement of the problem>

## Repos in scope

| Repo | Role |
|---|---|

## Investigations

| # | File | Covers | Status | Branches |
|---|---|---|---|---|
| 00 | [00_initial.md](00_initial.md) | <what this pass covers> | pending | — |

**How to read this series:** read every `NN_*.md` in serial order, lowest to highest, and
apply each file's `Supersedes` block as you go. The composition of all files in order is the
plan. This index is a summary and never a substitute for the files. Highest serial is newest
— never sort by modification time.

## Confirmed Assumptions
## Out of Scope
## Blast Radius
## Deployment & Rollout Notes
## Risk Assessment
## Open Questions
```

The sections after the TOC are the **reconciled** state after *all* passes — not a copy of
the newest file's sections.

### Provenance line

Every repo the investigation read, with the short SHA it was read at:

```bash
git -C <repo> rev-parse --short HEAD
```

This is what makes staleness mechanically checkable. `implement` uses it to scope its
drift re-check to what actually moved:

```bash
git -C <repo> log --oneline <sha>..HEAD
```

### Status column

Maintained by `implement`:

| Status | Meaning |
|---|---|
| `pending` | Not started. |
| `in progress <YYYY-MM-DD>` | Being implemented. |
| `implemented <YYYY-MM-DD>` | Done; the Branches column names what carried it. |
| `no code` | Turned out to need no change. |
| `superseded by NN` | A later serial invalidated it. |

Leave existing rows' Status and Branches alone except the ones this pass genuinely changes.

## Verification tiers

`implement` records the **best tier it actually reached** and never reports a lower tier as
"verified":

| Tier | Means |
|---|---|
| 1 — tests | The repo's own suite ran and passed. Name the command. |
| 2 — build | Compile, typecheck, or lint passed. No behavioural coverage. |
| 3 — run | The app was started and the change exercised by hand (the `run` skill). |
| 4 — manual | Steps handed to the user. Nothing was verified by the agent. |

State the tier, the command, and what it does **not** cover. "Tests pass" when only the build
ran is the specific failure this table exists to prevent.

## Writing rule: terse, invariant facts

Bullets over paragraphs. Record what the code does today, where it lives, and what the
constraint is — the things that stay true whichever option is chosen.

- Cite `file:line`. A claim with no citation and no command behind it is a guess.
- **Secrets: path and key, never value.** Investigation prose lands in git and evades the
  gates that catch structured secrets (sops, `kind: Secret` scanners). Name where a secret
  lives and what key it is under — never quote the value, a token, or a connection string
  with credentials embedded.
- `file:line` citations are **point-in-time**. `implement` re-verifies them against current
  `HEAD`; say so rather than implying they are durable.
- No restating the issue back. No "we should probably" — verify it and state it, or file it
  under Open Questions.
- Do not state counts ("13 lambdas", "22 call sites"). They rot silently and a reader who
  trusts a stale one is worse off than one who counts. Give the shape and how to derive the
  number. When correcting a stale count, remove it rather than refreshing it.
- **A claim from outside the codebase carries the primary source you actually read, or is
  marked secondhand.** `file:line` is what makes a code claim checkable; an external claim —
  a benchmark, a study, a vendor's number, a "best practice" — needs the same. Cite the paper,
  the docs page, or the post you opened. If you only have a summary of it, say so inline
  (*"secondhand — primary not read"*) and do not let the plan depend on it.

  Search-result snippets and vendor guides summarizing research are the common trap: their
  numbers arrive pre-formatted as findings and read as authoritative next to something you
  verified. A reader cannot tell the two apart unless you mark them.

## "Open Questions" is a last resort, not an inbox

Before a question is allowed into the section, triage it:

1. **Verifiable by you** → verify it now. Do not ask, do not park it. If the answer is in the
   code, a config, `git`, live infrastructure, or the docs, go and get it. "I could not tell
   from the code" is only true after you have actually looked.
2. **A requirement or scope decision** → ask it at the requirements gate. Anything shaped like
   "should we also…", "is X in scope", "which of these two behaviours" is a requirement, and
   requirements are settled before the plan is built.
3. **Genuinely external or blocked** → only now is it an Open Question.

When you record one, write: the question, **who owns it**, what decision it changes, and
whether it **blocks implementation**. A reader must never have to guess whether an Open
Question is a blocker.

## Interaction with `claude-sandbox init`

Verified against `claude-sandbox/internal/layout/layout.go`:

- `layout.Setup()` runs **only on `claude-sandbox init`**, never on launch. A project can be
  launched without the layout ever being scaffolded.
- It is idempotent `MkdirAll` and never deletes or moves. A pre-existing `investigations/`
  survives `init` untouched.
- **Never create `.claude-sandbox/CLAUDE.md`.** It is seeded once and never overwritten
  (CS-LAY-002), so creating it before `init` permanently suppresses the standard layout doc.
  Append a section if it already exists; otherwise leave it alone.
- No `.gitignore` entry is needed. `investigations/` is committed in both tracking modes,
  exactly like `reports/`: `trackInHost: true` ignores only `env`/`temp/`/`ralph/`;
  `trackInHost: false` ignores the whole dir in host git but the sidecar's own `.gitignore`
  also excludes only `temp/`/`env`/`ralph/`.
- **The `trackInHost` decision is made at `init`, after artifacts already exist.** In a repo
  that does not inherit `trackInHost: true`, a later `init` moves the directory out of host
  history into a sidecar repo. This cannot be fixed from the skill side.

**Public repos and deliberately-ignored `investigations/`:** when the repo is public, or its
`.gitignore` excludes `.claude-sandbox/investigations/` on purpose, the series lives in the
estate's sidecar meta-repo (`agents/investigations/<slug>/`) instead, and the invocation should
say so. The format is identical; only the home moves.

So: create the directory lazily with `mkdir -p`, never touch `CLAUDE.md`, and when
`.claude-sandbox/config.yaml` is absent, **warn once and continue** — do not hard-stop:

> `.claude-sandbox/` is not scaffolded (no `config.yaml`). Writing the investigation anyway.
> Run `claude-sandbox init` to scaffold the layout and settle whether this directory is
> tracked in the host repo or a sidecar.
